# DSH 翻译 — 安装说明

版本 **1.0.0** · Microsoft Edge（Chromium 内核，Chrome 也能用）

把网页翻成中文，推理全在 **DSH 的 NPU 插件**上跑。内容不出内网，不联网、不上传。

## 一、装（30 秒）

1. 解压到一个不会随手删掉的目录，例如 `D:\Tools\dsh-translate`
2. 打开 `edge://extensions/`
3. 左下角打开「**开发人员模式**」
4. 点「**加载解压缩的扩展**」，选中这个文件夹（里面能直接看到 manifest.json）
5. 固定到工具栏

> 不要拖压缩包进浏览器，必须先解压。

## 二、连（一步）

确保 DSH 面板里 **NPU 插件** 开着，然后：

**点扩展图标 → 点「一键连接」**

它会按这个顺序找：

1. 你上次填过 / 上次连成功过的地址
2. 浏览器能报告的本机局域网 IP（DSH 面板经常只绑网卡）
3. `http://127.0.0.1:47300` / `http://localhost:47300`
4. **兜底扫网段**：上面全不通时，扫常见网段的 47300 端口（16 路并发，254 个地址约 0.8 秒）

认的是 DSH 独有的自述接口（`GET /v1` 返回 `service: "dsh-npu"`），
所以不会把别的服务当成 DSH。连上会自动挑 **translate** 角色并试译一句。

> **为什么需要扫网段**：DSH 面板默认绑局域网网卡（实测 `192.168.1.3:47300`），
> 回环 `127.0.0.1:47300` 是关的；而 Edge 的 `chrome.system.network` 常常不可用，
> 拿不到本机 IP。这两个叠加起来，只试回环就永远连不上。

连不上再看这里：

| 情况 | 怎么办 |
|---|---|
| 面板绑在局域网 | 把面板上的 `http://192.168.x.x:47300` 填进设置页「DSH 地址」，首次保存会弹授权框点「允许」 |
| 自检报 404 model is not enabled | DSH 面板里 translate 槽位没加载，去面板启用 |
| 面板设了 token | 设置页填「访问 token」 |
| 其它 | 设置页点「测试一下」，它会逐条告诉你卡在哪一步 |

## 三、用

| 操作 | 效果 |
|---|---|
| `Alt+T` | 翻译 / 还原当前页面 |
| 选中一段文字后 `Alt+T` | 只翻这一段（浮在选区旁边的气泡里） |
| 右键「用 DSH 翻译选中的文字」 | 同上 |
| 弹窗「双语 / 仅译文」 | 切换显示方式，**不用重新翻译** |

## 四、设置里能改什么

| 项 | 说明 |
|---|---|
| DSH 地址 | 留空 = 自动发现 |
| 角色 | 默认 `translate`（专职翻译），也可用 `chat` |
| 默认显示方式 | 双语 / 仅译文 |
| 标签保护 | `[Digital]` `【R版】` `[汉化组]` 这类标签原样保留，不翻译 |
| 一次翻几段 | 默认 6。NPU 上一批约 0.6 秒 |
| 自动翻译 | 默认关（更可控），可加到特定站点 |
| 跳过的区域 | CSS 选择器，默认跳代码块和输入框 |

## 五、支持的文本格式

| 类别 | 内容 |
|---|---|
| 正文块 | 段落、标题、列表、引用、表格单元格、定义列表 |
| 行内语义 | `<b> <i> <u> <s> <code> <mark> <kbd> <sub> <sup> <cite> <q> <small> <abbr> <dfn> <samp> <var>` |
| 富文本容器 | 带 class 的 span（Discord 的 @提及、行内代码等） |
| 属性文本 | `alt`、`placeholder`、`aria-label`、`title`、`input[type=submit].value` |
| 表单 | `<option>` 选项文字、`<label>`、`<summary>`、`<figcaption>` |
| Shadow DOM | 开放的 shadowRoot 内部的文字和属性 |
| SVG | `<text>` 元素内容（原生替换，不破坏图形） |
| 主动跳过 | `<pre>` 代码块、脚本/样式、`translate="no"`、屏幕阅读器隐藏元素（clip/1px） |
| 站点导航壳 | Discord 的 `nav[aria-label="服务器侧栏"]`、`data-list-id="guildsnav"`、`data-list-id="channels"`、私信列表（整体跳过，一个元素都不碰） |
| 站点专名行 | nhentai / e-hentai 的 Artists / Groups / Parodies 行：键名照翻，**值（作者/社团/原作名）不翻** |

## 六、翻译缓存

翻过的内容存进扩展的本地数据库（`chrome.storage.local`，分 8 片存储），下次遇到直接复用：

| 类型 | 策略 |
|---|---|
| 独立单词 / 标签 / 按钮文字 | 翻一次即缓存，之后命中直接替换（零延迟） |
| 长句 | 第一次由模型翻译（那一次就是校准），结果缓存，之后同样直接替换 |
| 站点术语表 | e-hentai / nhentai 的数百个标签用固定译名，连模型都不用跑 |

缓存键做了归一化（去数字、压空白、统一大小写、去尾标点），所以
`big breasts 240.9k` 和 `big breasts 240.8k` 命中同一条。

按「命中次数 × 新近度」淘汰，上限 6000 条。设置页可以看条目数和清空。

## 七、实测性能

在 100 条的 Discord 式页面上（每条带 @提及、链接、行内代码）：

| 指标 | 数值 |
|---|---|
| 首个译文出现 | 0.4 秒 |
| 100 段翻完 | 2.2 秒 |
| 189 段大页面翻完 | 24.9 秒 |
| DSH 解码速度 | 130~160 tok/s |

并发 3 批比串行快 1.8 倍（60 段 17.3s → 9.8s）——DSH 的 router 虽然单 slot，但能重叠 prefill/decode。

## 八、设计取舍（为什么这么做）

- **多批并行**：DSH 单 slot，但同时排 4 批能让 prefill/decode 重叠，实测快 1.8 倍。
- **批大小 6**：实测 4/6/10/14 段的「每段耗时」几乎一样（290~320ms），6 段性价比最好。
- **编号行协议**：多段一次请求，模型按 `1. 2. 3.` 逐行返回，漏段能按编号定位并只补翻那一段。
- **标签保护**：送模型前把 `[Digital]` 换成占位符，翻完换回来，比「让模型别翻标签」可靠。
- **数字硬保护**：`@N0@` 这种可见 ASCII 标记锁住计数/金额/百分比/日期数字，翻完按序号还原。
  私用区字符（ 那类）实测会被模型直接吞掉，所以必须用模型看得见的标记。
- **同组打包**：标签云、键值对这类同类短文本按「组」一起送给模型，模型才知道上下文。
- **富文本保真**：`<b> <i> <a> <code> <mark> <kbd> <sub> <sup> <cite> <q> <small>` 等 20 种行内标签
  连同「带 class 的 span」（Discord 的 @提及、行内代码）都带进提示词，翻完按原节点还原。
  模型把 `<b>` 写成 `<strong>`、多写/少写、大小写混用都能容错；
  只有嵌套结构真错位时才退回纯文本，绝不错位 DOM。
- **元素级仅译文**：每个被翻的元素自己带标记，SPA（Discord 这类）重建 DOM 也不会打回双语。
- **translate="no" 只挡自己**：Discord 会给应用外壳加 `translate="no"` 来防浏览器整页翻译。
  如果把它当「整棵子树禁译」，走到外壳那层就整站不翻了 —— 所以只挡叶子，容器继续往下走。
- **aria-hidden 只挡装饰**：Discord 大量包裹层带 `aria-hidden` 但里面装着可见内容，只跳过没有子元素的纯装饰层。
- **窄元素原位替换**：侧栏频道名这类 32px 高的元素塞不下双语，自动改成「译文顶掉原文」，
  既不撑高也不被 ellipsis 裁；带图片的图标按钮则完全跳过，绝不破坏图形。
- **自动重连**：请求失败且是「连不上」时，会自动重新发现一次地址。


## 九、稳定性

同一段文本多次翻译必须给出一致结果 —— 这是「不太稳定」抱怨的根因：

| 措施 | 说明 |
|---|---|
| `temperature = 0` | 贪心解码，同输入同输出。实测同一标题连翻 6 次结果完全一致 |
| 缓存键保留数字 | 不同数字不共用条目（`Pages: 51` 和 `Pages: 26` 是两条） |
| 字母标签标记 | `«A» «B»` 不用数字，避免和数字保护打架 |
| 专名回退 | 保护完专名后若「可翻文字太少」，退回不保护 —— 宁可音译也不要整条不动 |
| 标题同组 | h1/h2 同一部作品的两种语言标题一起送模型，译名能对上 |


## 十、缓存卫生

持久缓存会因为「写进去的坏条目」导致某些行时好时坏。目前做了三道防护：

| 措施 | 说明 |
|---|---|
| 拒绝 identity 映射 | 译文 === 原文 的「结果」不写持久缓存 —— 那是失败，不是翻译 |
| 版本前缀 | 缓存键带 `CACHE_VER`，改了译法标准就把版本 +1，旧条目自动失效 |
| 加载即清理 | `diskLoad` 时丢弃无当前版本前缀的条目并回写 storage |

原因是旧版本确实写过一批 identity 记录（模型原样返回被当成成功），
之后永远命中它们 —— 表现就是「某些行一直不翻」。


## 十一、nhentai 改版适配（2026-11）

nhentai 在 2026 年改了标签区结构：

```html
<!-- 旧版 -->
<table id="gdd"><tr><td class="tc">Artists:</td><td>...chips...</td></tr></table>

<!-- 新版 -->
<section id="tags">
  <div>Categories: <span><a href="/category/doujinshi/">
    <span>doujinshi</span><span>519.5k</span>
  </a></span></div>
</section>
```

关键差异：**键名是裸文本节点，不是 `<td class="tc">`**。
旧规则找 `td/.tc/.field` 永远匹配不到，于是：

- 整行被当成一个单元送给模型
- 模型只翻了键名「Categories:」，chip 里的值原样返回
- 用户看到「类别: doujinshi 519.5k」这种半翻状态

修法：
1. `autoDetect` 从 `id="gdd"` 改成 `id="tags"`（两个都认）
2. 新增 `isLabeledChipRow()`：识别「裸文本键名 + 行内链接」的行，强制拆开
3. 新增 `label` 单元类型：键名（裸文本节点）单独翻，原位替换
4. 新增 `isBareTextOf()`：区分「键名」和「值」，专名行只跳过值


## 十二、页面结构分析器

遇到某个站点「部分行不翻」时，用它直接分析保存下来的 HTML：

```bash
# 1. 在浏览器里 Ctrl+S 保存页面（选「网页，仅 HTML」）
# 2. 分析
node test/analyze.js "C:\Users\me\Downloads\page.html"

# 想连真实 DSH 翻一遍看效果：
node test/analyze.js "C:\Users\me\Downloads\page.html" --translate
```

输出四张表：

| 表 | 内容 |
|---|---|
| 页面环境 | 站点规则、元素数、正文字数 |
| 会翻译的单元 | 每个单元的 mode（append/label/replace/inline/attr/option/svgtext）+ DOM 路径 |
| 被跳过的元素 | 每个的跳过原因（CSS 隐藏 / translate=no / aria-hidden / 代码块 / 专名行 / skipSelectors） |
| 实际译文 | `--translate` 时每条单元的原文 → 译文 |

外加一张截图（`<name>_analyzed.png`）。

判断方法：

- 某行**没出现在「会翻译的单元」里** → 看「被跳过的元素」表，找它和原因
- 某行**出现了但译文没变化** → 单元被送进模型了但模型原样返回，通常是纯专名
- 某行**译文位置错乱** → 看 mode 对不对（`label` 应该是原位替换，`replace` 是整块替换）

探测脚本拆在 `test/_page_*.js`（env / units / skips / results），改探测逻辑只改那几个文件，
不用碰主分析器。


## 十三、chip 计数不能进提示词

nhentai 的标签 chip 结构：

```html
<a class="tagchip">
  <span class="name">big breasts</span>
  <span class="count">240.9k</span>
</a>
```

如果把整条 `<a>` 收成一个单元，送进模型的是 `"big breasts 240.9k"`，后果：

| 问题 | 表现 |
|---|---|
| 术语表查不到 | 整串不匹配 `big breasts`，所以不走固定译名 |
| 数字保护被跳过 | 短文本（≤80 字）不保护，模型把 `240.9k` 翻成「240.9千」 |
| 语序被打乱 | `"big penis 35.5k"` → 「35.5千个大阴茎」 |

修法：新增 `chipNameEl()`，只收 `class="name"` 那个子元素。

```

✓ rape         → 强奸         ✓ double penetration → 双插
✓ mmf threesome → 两男一女     ✓ gang rape     → 轮奸

✓ tomboy       → 假小子       ✓ exposed clothing  → 暴露衣物
```

计数 `240.9k` 原样留在原 `<span class="count">` 里，模型完全不碰。


## 十四、日文 → 中文 的判定（重要）

原文里假名很多、译文里假名变少 —— 这是「确实翻了」的最可靠信号。

之前只看「汉字增长比例」，日文标题会被误判：

```
原文: [水龍敬] GTS グレートティーチャーサヨコ Lesson10 (…)
        han 12, kana 23
译文: [水龍敬] GTS 大師サヨコ Lesson10 (…)
        han 14, kana 13
汉字只多了 2 个 → 比例 0.033 < 0.15 → 判成「没翻」→ 译文被丢弃
```

现在加了「假名减少比例 ≥ 35% 就算翻了」这条判据。同一标题：

```
kana 23 → 13，掉了 43% → 已翻 ✓
```

实网验证（nhentai 695705）：

```
h1: [水龍敬] GTS 大師サヨコ Lesson10 (漫畫熱牛奶 2026年12月號) [古月个人汉化]
h2: [水龍敬] GTS 大師サヨコ 第10课 (コミックホットミルク 2026年12月号) [中文翻译]
```


## 十五、重复翻译的三个回归（2026-11-10 实网）

在真实 nhentai 页面上反复翻译后暴露的三个 bug：

### 1. 专名行判定失效 → 作者名被翻译

`label` 模式会把行首裸文本（"Artists:"）**清空**并替换成译文 span。
第二次翻译时 `inProperNounRow()` 读不到裸文本了 → 判定失效 →
「mizuryu kei」被当成普通标签翻成「美津留景」。

修法：裸文本为空时改读 `label` span 的 `data-dsh-src`。

### 2. `<time>` 标签名泄漏到页面

`<time>2 hours, 2 minutes ago</time>` 走富文本解析时，
`<time>` 被当成陌生标签处理 → 页面上露出 `&lt;time&gt;…&lt;/time&gt;` 字样。

修法：标签行的值容器强制 `rich = false`（那里没有需要保留的语义标签）。

### 3. `stop()` 不恢复 label 的裸文本

点了「还原」后键名不回来。已修（恢复 `labelNodes` 的 nodeValue 并移除译文 span）。


## 十六、两个「看起来没反应」的 UI bug（2026-11-10）

### 1. 设置页缓存区永远显示「读取中…」，清空按钮点了没反应

根因：`wireCache()` **定义了但从来没被调用**。

```js
function wireCache() {
  btn.addEventListener('click', ...)   // 绑定按钮
  refreshCache();                       // 首次读状态
}
// ...但初始化流程里没有 wireCache();
```

修法：在 `load()` 末尾调用。改完后真实浏览器实测：

```
点击前：628 条 · 约 52 KB
点击后：0 条 · 约 0 KB        ← 立刻刷新
```

### 2. 清空缓存之后又「长回来」

根因：`cacheClearAll()` 清了内存和 storage，但**没取消待处理的 flush 定时器**。
2 秒后定时器触发，`diskFlush()` 遍历 `S.disk` 把（此时已空的）数据写回 storage——
看着像没清掉，实际是统计计数器没重置。

修法：
- `clearTimeout(S.diskTimer)`
- 统计计数器清零（`S.hits / l1hits / l2hits / glossHits`）
- 页面术语参考 `S.recentTerms = []` 一起清
- `broadcastRaw({ t: 'cacheCleared' })` 通知页面重置本地键

注意：`broadcast(cfg)` 的参数是**配置对象**，直接传消息会被包成
`{t:'dsh-config', cfg:{...}}`，页面收不到。所以新增了 `broadcastRaw(msg)`。

## 十七、提示词卫生：参考材料绝不能进 user 消息

真实截图暴露的 bug：页面上冒出这样一串文字——

```
本页面已使用的术语（重复相同渲染方式，不再翻译）：- 3小时27分钟前
(2026年11月10日) = 3小时27分钟前 (2026年11月10日)
```

这是模型把我写在 user 消息里的英文提示**当成待翻内容译了出来**。

修法：

| 位置 | 之前 | 现在 |
|---|---|---|
| 术语参考 | user 消息开头 | **system 消息末尾** |
| 旧译参考 | user 消息开头 | **system 消息末尾** |
| 垃圾词条 | 全部收进参考 | **中文源/identity 一律过滤** |

system 是「指令区」，模型只遵守不输出。实测（同一句）：

```
输入: 1 hour, 27 minutes ago (2026年11月10日)
输出: 1小时27分钟前（2026年11月10日）   ← 干净，无泄漏
```


## 十八、数字保护阈值必须按「可见文字」算

```js
// 错
if (t.length <= 80) return t;

// 对
var visible = stripTags(String(t).replace(/<[^>]*>/g, '')).length;
if (visible <= 80) return t;
```

富文本标题带标签：

```
<span class="before">[水龍敬] </span><span class="pretty">GTS グレートティーチャーサヨコ Lesson10</span>...
↑ 原始长度 147 字，可见文字只有 64 字
```

用 147 判断 → 触发数字保护 → `@N0@` 被模型当成序号 →

```
第0课 (Comic Hot Milk 第1年第2月刊)   ← 灾难
```

改用 64 判断 → 不保护 → 数字原样保留 ∧ 模型正常翻译：

```
第10课 (漫画热牛奶 2026年12月期)       ← 正确
```

5 次实测全一致，无序号化、数字完整。

### 顺便验证了标记形态

对同一段含 11 个数字的长句，测四种占位符模型保留率：

| 标记 | 保留 |
|---|---|
| `@N0@` | 11/11 |
| `@A@` | 11/11 |
| `⟦A⟧` | 11/11 |
| `«A»` | **0/11** |

`«A»` 是标签保护用的标记，模型认得它会照抄；但**和数字混用会全丢**。
数字保护必须用不同的标记族，当前用 `@N0@` 是对的。

### 部分还原

模型有时只吐出 10/11 个占位符。原来只在「全部丢失」时才补回数字，

## 十九、自动翻译改成白名单机制（2026-11-11）

### 为什么改

原来是黑名单（`autoOffSites`）：打开「自动翻译」后，**没列过的站全都自动翻**。
等于「默认全开」——浪费 NPU 算力，还可能在用户不想翻的站上乱翻。

改成白名单：**只有明确列过的站才自动翻**，没列的一律不翻（默认全关）。

优先级：

```
autoTranslate 关闭   → 全部不自动翻
autoOffSites 命中    → 不自动翻（最高优先级）
autoOnSites 命中     → 自动翻
都不在               → 不自动翻
```

### 弹窗加了开关

原来只能在设置页手填 URL，太麻烦。现在 `popup.html` 加了「本站自动翻译」开关：

```
本站自动翻译              [○──]
默认关闭 · 走白名单
```

- 拨开：把当前 origin 加进 `autoOnSites`，**顺带把总开关也打开**（否则白名单形同虚设）
- 拨开时如果当前页还没翻译，立刻翻一遍
- 拨关：从 `autoOnSites` 移除
- 本地页 / `edge://` / 扩展页：开关禁用并提示「本地/内置页面不适用」

### 消息接口

| 消息 | 作用 |
|---|---|
| `getSiteAuto {origin}` | 查当前站是否在白名单（含总数开关状态） |
| `setSiteAuto {origin, enabled}` | 加/移白名单，自动处理与黑名单的互斥 |

实测（真实浏览器）：

```
初始:   {enabled:false, onSites:[], globalOn:false}
打开:   {enabled:true,  onSites:["https://nhentai.net"], globalOn:true}
再查:   {enabled:true,  onSites:["https://nhentai.net"], globalOn:true}
关闭:   {enabled:false, onSites:[], globalOn:true}
```

reload 页面验证自动翻生效：

```
reload 后: mode=only, total=117, done=32（翻译中）   ← 白名单生效
```


## 二十、下拉框统一样式（2026-11-11）

原生 `<select>` 的**展开面板由操作系统绘制**，Edge 默认按系统主题画成浅色白底 ——
跟暗色界面完全不搭。

### 解法一：appearance: base-select（Chromium 135+）

Edge 157 已支持。开启后整个 `<select>`（含展开面板 `::picker(select)`）都能被 CSS 控制：

```css
.ui-select,
.ui-select::picker(select) { appearance: base-select; }

.ui-select::picker(select) {
  margin-top: 6px;
  padding: 5px;
  background: var(--panel-2);
  border: 1px solid var(--line);
  border-radius: 11px;
  box-shadow: 0 10px 28px rgba(0, 0, 0, 0.5);
}

.ui-select option { padding: 7px 10px; border-radius: 7px; }
.ui-select option:checked { background: rgba(107,140,255,0.18); }
```

效果：面板是深色圆角卡片、选项整行圆角高亮、选中项前面有勾、箭头展开时旋转 180°。

### 解法二：color-scheme: dark（降级）

旧浏览器不支持 base-select 时，声明 `color-scheme: dark` 让系统把面板画成深色，
再配 `appearance: none` + 自绘 SVG 箭头，收起态保持完全一致。

两套用 `@supports (appearance: base-select)` 隔开，渐进增强，旧版不会炸。

### 踩到的一个坑

base-select 下浏览器会给选中项画一个**原生勾**（`::checkmark`）。
我又用 `::before` 自绘了一个 → 出现两个 ✓。

修法：

```css
.ui-select option::checkmark { display: none; }   /* 关掉原生的 */
.ui-select option:checked::before { content: "✓"; }  /* 只留自绘的 */
```

还要给未选项留同样宽度的 `::before` 占位格，否则「有勾/没勾」时文字会左右跳动。

## 二十三、图片翻译（v3.0.0）

**按住 Alt 点图片** → 图里的文字翻成中文并盖在原处。

### 为什么不用 OCR 工具

传统做法是 `OCR → 文本清洗 → 翻译模型` 三级流水线，需要部署 Tesseract/PaddleOCR。

这里用**纯浏览器算法定位文字 + 多模态模型直接翻译**：

```
① 灰度化 + 二值化（阈值 150）
② 连通域分析（行扫描 + union-find）
③ 剔除超大块 / 长线条 / 过小噪点 / 中空形状（气泡边框）
④ 两级聚类：字形 → 行 → 文字块
⑤ 逐块裁剪 → translate 角色（带 mmproj，能直接看图）
⑥ overlay 盖译文，字号自适应
```

### 实测性能

| 步骤 | 耗时 |
|---|---|
| CV 检测（900×1200 漫画页） | **17 ms** |
| 逐块翻译（4 块串行） | 355~455 ms |
| **合计** | **~470 ms** |

检测准确率：4 个气泡的 bbox 与真实位置偏差 **≤ 1px**。

### 关键技术点

**两级聚类**（这是质量的分水岭）：

只做一级聚类（按行）会把同一气泡的 2 行拆成 2 块 → 8 块半句话 → 模型缺上下文瞎猜：

```
これは本当に    → "这是真的。"      （丢了后半句）
すごいね！      → "不错！"
ございます      → "谢谢"           （敬语后缀被当独立句子）
明日ね          → "明天ね"         （半中半日）
```

两级聚类合并成一个气泡后：

```
これは本当にすごいね！  → "这真的太好了！"    ✓
ありがとうございます    → "谢谢 您辛苦了"      ✓
```

**中空形状过滤**（fill ratio < 0.02）：

实测数据定阈值：

```
页面边框  900x1185  n=2359  fill=0.002
椭圆气泡  401x181   n=356   fill=0.005   ← 之前被当成"文字块"的就是它
单个字符  26x25     n=50    fill=0.048~0.10
```

**字号自适应**：

CSS 用固定 clamp 会算出一个平均值，块小的时候溢出。改成 JS 按块宽高算：

```
每行字数 = 块宽 / 字号
行数     = 字数 / 每行字数
总高度   = 行数 × 字号 × 1.25
```

优先「单行放得下」——中文没有词间空格，浏览器按字符断行，会切成「你好！今天做什」/「么?」。

宽度估算必须把**中文标点算全角**（！？、。都是 1em），否则算出来偏小 → 字号偏大 → 又换行。

**去重复**：

2B 模型会把同一句吐两遍（「明天吧 明天吧」）。三层防护：
1. `repeat_penalty: 1.22`
2. prompt 里「不要重复」
3. `dedupeLines()` 后处理（保留中文叠词「啊啊啊啊」）

### 触发方式

**Alt + 点图**，不是普通点击。原因：页面上大量图片是可点的（商品图、头像、缩略图），
拦截单击会破坏导航。Alt+点 是用户主动意图。

### 跨域图

`canvas.toDataURL` 在跨域图上会抛异常（canvas 被污染）。检测到后明确提示：

> 这张图跨域，浏览器不允许读取像素。可以右键「复制图片地址」在新标签打开后再试。

### 还原

面板右上角有「还原」按钮，一键清掉所有 overlay。


## 二十四、跨域图修复（v3.1.0）

### 用户报告的症状

> nhentai.net/g/695718/3/ 使用 Alt+鼠标左键无效

### 根因（两个，叠在一起）

**① 带修饰键的 click 可能被页面 preventDefault 吞掉**

原来的触发是 `document.addEventListener('click', ...)`。

很多漫画站 / 图床在 `mousedown` 里做 `preventDefault()`（防拖拽保存图片）。
浏览器规定：如果 mousedown 被 preventDefault，**click 不再派发**。
于是 Alt+点击时，click 事件根本没到扩展。

修：改成监听 **mousedown**（点击序列第一环，拦不住）。
代价是比 click 早 100~200ms，对图片翻译反而是好事（松手前就开始检测）。
click 作为兜底保留，用 `S.lastTrigger` 去重。

**② nhentai 的图跨域，canvas 被 taint**

```
页面   https://nhentai.net/g/695718/3/
图片   https://i4.nhentai.net/galleries/4314521/3.webp
```

把这种图 drawImage 到 canvas 后，canvas 被标记 tainted：

```
Uncaught DOMException: Failed to execute 'getImageData' on
'CanvasRenderingContext2D': The canvas has been tainted by cross-origin data.
```

任何 `getImageData` / `toDataURL` 都抛异常 → 检测直接失败 → 什么都画不出来。

### 解法

在 **background** 里 fetch 图片。background 的 fetch 走扩展的
`host_permissions`（manifest 里已是所有 http/https 域名），**不受页面同源策略限制**。

```
content script  →  chrome.runtime.sendMessage({t:'fetchImage', url})
background      →  fetch(url) → blob → FileReader → dataURL
content script  ←  dataURL（同源，画进 canvas 不再污染）
```

实测 nhentai 的漫画页（1280×1811 webp，148 KB）：**15 ms** 抓完。

### 现在的工作流

```
Alt+点击图片
  ↓
① 1x1 canvas 快速试探（同源图直接过）
  ↓ 失败 = tainted
② background fetchImage → dataURL
  ↓
③ dataURL → Image 对象
  ↓
④ CV 检测（5~20ms）
  ↓
⑤ 逐块裁剪 → translate（带 mmproj）
  ↓
⑥ overlay 盖译文
```


```
目标语言    : 简体中文
```

## 二十五、真凶：nhentai 的透明覆盖层（v3.2.0）

### 用户报告

> nhentai.net/g/695718/3/ 使用 Alt+鼠标左键无效
> （图片页面已 Ctrl+F5 刷新，依旧无反应）

### 诊断过程

用户敲 `__DSH_IMG_DIAG()` 拿到关键信息：

```

翻译器接线 : ✅   跨域抓图 : ✅

```

前置条件全绿，但一次都没触发过。

### 根因：点到的不是 IMG

nhentai 的阅读器在图上盖了一层**透明 div**（用来做「点左半屏翻上一页、
右半屏下一页」、拖拽平移、双击缩放）。

用户视觉上「点的是图」，但 `e.target` 是那层 div：

```js
if (t.tagName !== 'IMG') return;   // ← 旧代码在这里直接 return
```

漫画阅读器/图床常见三种「点不到 IMG」：

| 场景 | e.target |
|---|---|
| 图上盖透明层（翻页热区） | `<div>` |
| 图包在链接里，点在 padding 区 | `<a>` |
| 点在图容器留白 | 父容器 |

### 修法：`resolveTargetImage` 四级反查

```
① target 本身是 IMG          → 用它
② target 有 IMG 祖先         → 最近的 IMG 祖先
③ target 是覆盖层            → document.elementsFromPoint 拿该点所有层叠元素，
                              找第一个 IMG（能穿透覆盖层）
④ 都没有                     → target 所在容器里找第一张够大的 IMG
```

还要处理 `background-image` 显示漫画页的阅读器（没有裸 `<img>`）——
从 `getComputedStyle` 的 `backgroundImage` 里抽 URL。

## 二十六、右键菜单：可靠的图片翻译入口（v3.3.0）

### 背景

Alt+点击在有些页面**永远不灵**：

| 情况 | 为什么 |

这说明 Alt 键在这个环境里就被截住了。

### 解法：右键菜单

右键菜单是**浏览器层**的，不依赖页面事件：

| 优势 | 说明 |
|---|---|
| 不受 preventDefault 影响 | 菜单由浏览器绘制 |
| 不受覆盖层影响 | `info.srcUrl` 由浏览器直接给真实图地址 |
| 不受 Alt 被截获影响 | 不需要修饰键 |
| 穿透 iframe | `contexts: ['image']` 在子框架也能命中 |

### 四项菜单

| 位置 | 菜单项 | 动作 |
|---|---|---|
| 图片上右键 | 用 DSH 翻译这张图的文字 | 按 `info.srcUrl` + 坐标反查图 → 翻译 |
| 选中文字右键 | 用 DSH 翻译选中的文字 | 弹气泡 |
| 页面空白右键 | 用 DSH 翻译整页 | 开始整页翻译 |
| 页面空白右键 | 还原页面 / 关闭图片译文 | 停止并清除 overlay |

### 踩到的坑：菜单注册不幂等

原来的实现只在 `onInstalled` 里创建一次。问题：

1. Edge「重载未打包扩展」时 `onInstalled` **不一定触发** → 菜单消失
2. `removeAll()` 回调里立刻 `create()` → 撞 `Cannot create item with duplicate id`
3. 加 50ms 延时 → **仍可能失败**（SW 刚启动时 `chrome.contextMenus` 还没就绪）

实测数据：

| 策略 | 结果 |
|---|---|
| `removeAll` → 立即 create | 4 个里 3 个失败 |
| `removeAll` → 50ms 后 create | 仍失败 |
| `removeAll` → 200ms 后 create | OK |
| `removeAll` → 250ms 后 create | OK（采用） |

**最终策略：先试创建，撞车才 removeAll 重试**

```js
// 1. 逐项 create
// 2. 报 duplicate → removeAll → 250ms → 全部重建
// 3. 无冲突就直接成功（SW 重启且菜单还在时的常见路径）
```

注册时机：`onInstalled` + `onStartup` + SW 冷启动，三处都调。

## 二十七、图像描述污染：最严重的一次翻译事故（v3.4.0）

### 用户报告

> 翻译出问题了

配图：真实 nhentai 漫画页，7 个块全被盖上了**图像描述**而不是译文：

```
画面中：山崎说到：你吃了吗？吃了吗？旁边写着山崎说到和女面商会
画面中有一处细节：一个带有标签的容器旁边写着「かっ？」（日语）
这位角色的上半身画面中可以看到她穿着带有花纹的日式和服式上衣
图片中的文本无法显示或无效。
图片中的文本已全部翻译成简体中文；图像中没有任何可见的文本内容。
```

### 三个叠加的根因

**① 检测把插画当成了文字块**

原来的 `fill ratio` 只有**下界**检查（`fill < 0.02` 剔除中空边框），
但**实心色块**（角色插画、阴影、黑衣）fill ≈ 1.0，**从另一边穿过去了**。

于是 641×329 的插画区域被当成"文字块"，占图 15%。

**② 大块 → 模型走 captioning**

送进一个大部分是画面、只有零星文字的 crop，多模态模型会倾向
**描述画面**而不是 OCR。2B 模型尤其如此。

**③ prompt 里的 few-shot 示例被照抄**

原来为了让格式稳定，在 prompt 末尾加了：

```
示例输出：
你好，今天做什么？
这个真的很好！
```

实测：模型把示例当成**标准答案**，遇到纯插画也原样吐出这两句：

```
插画块 → "您好，今天做什么？这真的很不错！"
```

这是小模型 few-shot 的经典陷阱：**大模型参考格式，2B 模型照抄内容**。

### 四层修复

**层 1：检测加 fill 上界**

```js
if (fill > 0.55 && (w * h) > 400) continue;   // 实心块 = 插画
```

阈值标定（PIL 造的真实漫画页 + 用户数据）：

| 内容 | fill ratio |
|---|---|
| 文字笔画 | 0.03 ~ 0.30 |
| 抗锯齿粗体字 | 0.30 ~ 0.45 |
| **实心插画块** | **0.85 ~ 1.00** |

0.55 落在 0.45 和 0.85 之间，两边都有余量。

**层 2：超大块拆回单行**

```js
var tooBig = (w * h > area * 0.06) || (h > 400);
if (tooBig) { 拆成每一行各自成块 }
```

单行 bbox 只含那一行文字，几乎不含插画 → 模型不会描述画面。
代价是丢上下文（逐行翻会生硬），但**「生硬但正确」远好于「流畅的图像描述」**。

**层 3：prompt 重写**

```
这是文字识别（OCR）与翻译任务，不是图片理解任务。
1) 只输出译文，不要输出原文；
2) 不要描述画面内容（不要写「画面中」「可以看到」「穿着」「背景」这类描述）；
3) 不要解释、不要重复；
4) 一行对应一行，保持换行结构；
5) 如果图中确实没有任何文字，只输出「（无文字）」。
```

**关键：删掉所有示例**（层 3 的教训）。

**层 4：后处理过滤**

`looksLikeCaption()` —— 识别并丢弃图像描述：

```js
var CAPTION_MARKERS = [
  /画面中/, /图片中/, /图像中/, /图中/, ...      // 指代整图
  /可以看到/, /穿着/, /背景是/, /站在/, ...      // 视觉叙述
  /无法显示/, /没有可见/, /未检测到/, ...        // 自我否定
  /已全部翻译/, /文本已全部/                      // 自我宣告
];
```

还有 `extractUsableImageText()` 做完整流程：
剥双段落 → 去重复 → **逐行剔除描述** → 检查「（无文字）」占位符。

**混合输出也能救回来**：

```
"你好！ / 画面中可以看到她穿着和服。 / 谢谢"
  → "你好！ / 谢谢"
```

### 被跳过时的 UI

```
[2] （这块被跳过）
```

## 二十八、填充问题 + 竖排日文（v3.5.0）

用户下载真实漫画页到 `C:\Users\123\OneDrive\图片\test.png`（1280×1810）实测。

### 问题 1：白底把插画盖住了

截图里那个 11.3% 面积的巨型白框，就是「填充问题」。

**根因：一级聚类雪球**

旧判据是 `垂直重叠 / min(簇高, 字形高) ≥ 0.45`。簇长到 202px 后，
`min(202, 28) = 28` —— 任何 28px 的字只要和这个 202px 的簇垂直重叠
12.6px 就算「同一行」。**簇越胖越容易吸收，最终 bbox 撑成整块插画。**

实测产出的「行」：

| bbox | 真实含义 |
|---|---|
| (355,0) 868×202 | 胸部插画（网点纸） |
| (338,243) 885×165 | 更多网点 |
| (150,495) 1022×256 | 插画 + 三列竖排混在一起 |
| (244,1180) 779×160 | 整张脸 |

### 问题 2：竖排日文（tategaki）

这是日式漫画的常态。旧算法只做**水平**方向聚类，所以：

- 同一 y 范围的 3 个竖排列被当成「一行」→ 合并成巨型框
- `w/h < 1.1 → 跳过` 又把竖排块全丢掉

### 修复 1：紧邻图聚类（complete rewrite）

```
字形 →【紧邻图】→ atom →【分类】→ 竖列/横排/丢弃 →【合并】→ 段落
```

**第一步：字形 → atom（union-find，双方向连边）**

```js
// 水平紧邻：x 间距 ≤ 0.7 字高，垂直重叠 ≥ 40%
// 垂直紧邻：y 间距 ≤ 0.7 字宽，水平重叠 ≥ 40%
```

关键：**传递闭包**。一列竖排的 5 个假名会连成一个 atom，
一行横排的 6 个汉字也连成一个 atom。**不需要事先知道方向**。

用空间哈希（cell 网格）只比较邻近 bucket，避免 O(n²)。
实测 1614 个字形只要 **54ms**。

**第二步：atom → 分类（用 p90 字符尺寸）**

| 形态 | 判据 |
|---|---|
| 竖列 | 宽 ≤ 2.5 字宽，高 1.6~30 字高 |
| 横排 | 高 ≤ 2.5 字高，宽 1.6~40 字宽 |
| 网点/插画 | 两者都超 → **丢弃** |

**为什么用 p90 而不是中位数**：网点纸贡献了大量 8px 的假「字形」，
把中位数拉到 8px，而真正的假名/汉字是 23px。用 8px 做基准会双向都错。

实测分开得很干净：

| atom | 宽/p90W | 高/p90H | 判定 |
|---|---|---|---|
| 真竖排列 33×137 | 1.4 | 5.7 | ✓ 文字 |
| 真竖排列 29×353 | 1.3 | 14.7 | ✓ 文字 |
| 网点块 478×169 | 20.8 | 7.0 | ✗ 宽度超 |
| 网点块 297×193 | 12.9 | 8.0 | ✗ 丢弃 |

**第三步：同向 atom 合并成段落**

竖排的语义单元是整句（多列一起读），单列送模型只能翻半句。

| | 修复前 | 修复后 |
|---|---|---|
| 检测块数 | 4 个巨型框 | 11 个精确块 |
| 最大块面积 | **11.3%**（盖住插画） | **2.6%**（正常气泡） |
| 竖排 | 全部丢失 | 正确识别为竖列 |

### 修复 2：两阶段流水线（vision OCR + translate 翻译）

修好检测后，竖排块送模型，**翻译全错**：

```
原文 どうですか？私の料理は採れたてのものを用意しました
→ 译文「您是否已经使用过那个东西？我的材料是……」  ✗
```

试过的方案（都无效）：

| 方案 | 结果 |
|---|---|
| 整块送（三列竖排） | 识别就错（「どうれたどうてですかのと？」） |
| 旋转 90° | 更糟（模型没见过旋转的假名） |
| 拆成单列 | 单列识别也错 |

**真正的解法：让 OCR 和翻译分开。**

实测 OCR 能力对比（同一批竖排日文，只让模型「照抄原文」）：

| 模型 | 整块三列 | 单列 | 短竖排 |
|---|---|---|---|
| translate (Index-Translate-2B) | ✗ 支离破碎 | ✗ | ✗ |
| **vision (LFM3-Omni-2B)** | **✓ 完全正确** | **✓** | **✓** |

然后 translate 做纯文本翻译，质量立刻上来了：

```
vision OCR   → どうですか？私の料理は採れたてのものを用意しました
translate    → 怎么样？我用了最新鲜的食材做的菜。          ✓
```

速度：**197~323ms**（OCR 89~190ms + 翻译 108~165ms）。
比一步到位多一次请求，但结果从「全错」变「全对」。

### 实现

```js
async function visionTwoStage(base, cfg, dataUrl, opts) {
  // ① vision 做 OCR（只照抄，不翻译）
  const ocr = await chatVision(base, cfg, 'vision', OCR_PROMPT, dataUrl);
  if (!ocr || 无文字) return { skipped: true };

  // ② translate 做翻译（纯文本，不带图 → 更快）
  const trans = await chatText(base, cfg, 'translate', buildTextTranslatePrompt(ocr, lang));
  return { text: extractUsableImageText(trans), src: ocr, ocrMs, transMs };
}
```

配置可关（`twoStage: false` 退回一步到位），OCR 失败也自动退回。

### 已知限制

3 个气泡依然漏检（「いやあ、本当に助かるよ〜」「まだまだお代わりはあるので」

二值化后粘连，连通域巨大被面积阈值杀掉。

纯 CV 方案解不了这个，需要深度学习 OCR（PaddleOCR 之类）。
试过局部自适应阈值（BoxBlur 15），网点区域和文字区域的响应完全重叠，分不开。

## 二十九、更简单的方案：整页模式（v3.6.0）

「有没有更简单的图→图翻译？」——查了一整轮，结论分两半。

### 先否定：一步到位给 bbox 不可行

让 vision 模型直接输出 `[{box, src, zh}]`，实测（真实漫画页）：

| 尝试 | 结果 |
|---|---|
| bbox 用像素坐标 | 框全错，有的负宽度 |
| bbox 用 0~1 归一化 | 模型仍按 0~1000 输出，且位置漂移 400px |
| bbox 用 0~1000 | 位置勉强对，但同一段被拆成 3 个碎片 |

实测数据（真实坐标 vs 模型给的）：

```
山海経      真实 (1195,80)-(1225,310)   模型 (1168,50)-(1256,358)  ← 宽了 3 倍
どうですか   真实 (945,33)-(1010,440)    模型 (938,438)-(1017,474)  ← y 差 400px
あので、     ——                         模型 (1015,981)-(1004,999) ← x1>x2 非法
```

**这个 2B 模型没有 grounding 能力。** 一步到位的图→图在这条路上走不通。

### 再肯定：整页 OCR + 整页翻译（列表展示）

这条路是通的，而且**更简单、覆盖更全**。

```
① vision 整页 OCR（一次请求）
② translate 整页翻译（一次请求，编号对齐）
③ 面板列表展示
```

### 关键：提示词必须锁死分段规则

实测（同一张图，3 次重复）：

| 提示词 | 分段数 | 稳定性 |
|---|---|---|
| 「按阅读顺序逐段输出」 | 11 段 / 19 段 / 11 段 | **不稳定** |
| 「一个气泡一行，不要按物理换行拆开」 | 8 段 / 8 段 / 8 段 | **完全一致** |

模糊的说法模型会自由发挥；明确「一个气泡 = 一行」才稳。

### 关键：翻译必须用编号对齐

实测（同一批 19 行输入）：

| 提示词 | 输出行数 |
|---|---|
| 「输出必须一行对一行」 | 13 行（模型自己合并了） |
| 「必须保留每行开头的编号」 | **19 行（完全对齐）** |

2B 模型对「行数守恒」这种抽象约束不可靠，但对「保留编号」这种显式锚点很听话。

### 效果对比

| | 逐块模式 | **整页模式** |
|---|---|---|
| 气泡覆盖 | 4/7（网点背景漏检） | **7/7** |
| 耗时 | 1873ms | **1924ms** |
| 能否原位替换 | 能 | 不能 |
| 译文连贯性 | 差（半句话独立翻） | **好（有整页上下文）** |

```
   → 最近太忙了，根本没好好吃过东西。

   → 还没呢，有替代品，你喜欢的话就只吃这个吧。

   → 哦，那就让我试试吧。
```

### 怎么用

| 操作 | 模式 |
|---|---|
| **右键图片 → 「用 DSH 翻译这张图的文字」** | 逐块（原位盖译文） |

## 三十、最终解法：形态学方向闭运算（v3.7.0）

### 试过的所有模型方案（全部否决）

| 方案 | 问题 |
|---|---|
| Florence-2 (0.23B) | llama.cpp 不支持 BART 架构 |
| Grounding DINO Tiny (0.17B) | llama.cpp 不支持 DETR |
| PaddleOCR-VL-1.6 GGUF | 实测不给 bbox（三种 prompt 全退化） |
| GLM-OCR 0.9B GGUF | 实测不给 bbox |
| LightOnOCR-2-bbox | 定位的是插图不是文字 |
| Surya-det (23MB) | 需要 CrispEmbed/ONNX-web，违反「不引第三方」 |
| Qwen2.5-VL | 能跑，但 bbox 精度差 400px |

**结论：llama.cpp 生态里的模型都不给可靠文字 bbox。**

### 真正的解法：纯 JS 形态学

**方向性闭运算**（先沿单方向膨胀 k，再腐蚀 k）。

```
闭运算 = 不创造新形状，只把「沿该方向距离 < 2k 的两块」桥接
```

为什么它对网点纸天然免疫：

| | 竖排日文 | 网点纸 |
|---|---|---|
| 字符垂直间距 | 0~5px | —— |
| 纵向膨胀 12px 后 | **桥接成长条** | 还是方块 |
| 腐蚀回来后 | 28px 宽的长条 | 长宽比接近 1 |
| 判据 h/w >= 2.5 | 通过 | 被滤掉 |

### 踩到的坑：腐蚀必须逐窗口

一开始我把腐蚀写成「只看窗口两端各一个点」：

```js
ero[x] = dil[x-k] && dil[x+k];     // 错！
```

这在 k>1 时不等价 —— 窗口两端是前景，中间可能有大洞。

正确实现用「最近的非前景位置」：

```js
var lastZero = -1;
for (x = 0; x < W; x++) {
  if (!dil[off + x]) lastZero = x;
  ero[off + x] = (lastZero < x - k) ? 1 : 0;   // 窗口内全是前景
}
```

**实测差异巨大：**

| 腐蚀实现 | 检出的条 | 最终段落 |
|---|---|---|
| 只看两端（错） | 6 条 | 6 段，最大 0.14% |
| 逐窗口（对） | **26 条** | **12 段，覆盖全部 7 个气泡** |

### 双阈值二值化

形态学要用更严格的阈值（120 而非 150）：

| 阈值 | 文字前景 | 网点前景 | 形态学效果 |
|---|---|---|---|
| 150 | 7~17% | 24~32% | 网点也桥接 → 全被滤掉，只剩 6 条 |
| **120** | 7~17% | 12~20% | 文字桥接、网点不桥接 → 26 条 |

所以 `binarize()` 现在生成两张图：
- `bw`（阈值 150）→ 给逐字形分析用
- `bwDark`（阈值 120）→ 给形态学用

### 效果

| 指标 | union-find（旧） | 形态学（新） |
|---|---|---|
| 检出气泡 | 4 / 7 | **7 / 7** |
| 最大块面积 | 2.6% | 2.70%（正常气泡大小） |
| 检测耗时 | 44ms | 82ms（morph 只占 36ms） |
| 外部依赖 | 无 | **无** |

实测翻译（1280×1810 真实漫画页）：


### 为什么这个方案是对的

- **零依赖**：纯 JS，不需要任何模型/库/服务
- **零下载**：不占用户带宽
- **快**：36ms（比加载一个 23MB 模型快得多）

## 三十二、翻页清场（v3.9.0）

### 用户报的问题

> 切换第二张图片，文字没有清空、重新读取翻译

### 根因（两层）

**层 1：三个入口只清面板，不清 overlay**

```js
// 之前每个 translate*() 开头都是这句
panel.querySelector('.dsh-ip-body').innerHTML = '';
```

只清了**面板列表**，但没清 **overlay 图层**（`.dsh-imglayer`）。
于是翻页后旧译文还挂在图上。

**层 2（更根本）：翻页时根本没调 translate**

用户翻页时只是 `<img>` 的 `src` 变了，**不会触发任何翻译函数**。
所以「入口清理」修得再干净也没用 —— 旧 overlay 会一直挂着，
直到用户手动再点一次翻译。

### 修复 1：统一清场 `beginTranslate()`

三个入口（CV / 整页 / 版面）开头都调：

```js
function beginTranslate(firstStat) {
  S.seq++;                                    // ① 中断上一次
  document.querySelectorAll('.dsh-imglayer')  // ② 清所有 overlay
    .forEach(l => l.remove());
  S.curLayer = S.curImg = S.lastImg = null;   // ③ 重置状态
  panel.querySelector('.dsh-ip-body').innerHTML = '';  // ④ 清面板
  return S.seq;
}
```

顺带修掉一个**隐藏 bug**：`translateImage` 里有两处 `++S.seq`，
第二处会把自己刚拿到的 seq 顶掉 → 第一块翻译刚开始就判定「已中断」。

### 修复 2：监听图片变化 `bindImageChangeCleanup()`

这是根本修复。三个信号都接：

| 信号 | 覆盖场景 |
|---|---|
| `load`（捕获） | img 换 src 且加载完成（最可靠） |
| `error`（捕获） | 加载失败也要清（否则旧译文永远挂着） |
| `MutationObserver`（src/srcset） | 换了地址但还没加载完的空窗期 |

一变化立即：清 overlay + 清面板 + 中断翻译 + 面板提示「图片已切换，请重新翻译」。

```js
'div:has(> [class*="messageContent_"]) [class*="timestamp"]',
'div:has(> [class*="messageContent_"]) time[datetime]',
```

**② 文本启发式兜底**（结构变了也能挡）

```js
isDateTimeOnly(text)  // 纯日期/时间/ID
  2024/9/18 · 09:55 · 今天 09:55 · 3分钟前 · 刚刚 · 14790024850480480266

isMetaLine(text)      // 名字 + 时间形态
  Deleted User  2024/9/18 09:55
  Honeybot 2024/9/18
```

**为什么需要两层**：Discord 改版频繁，纯 selector 会失效；但「这段文字是不是时间戳」可以从内容判断，那是稳定的。

### 踩过的两个坑

**坑 1：后代选择器抓不到兄弟节点**

```js
'[class*="messageContent_"] [class*="header_"]'   // ← 匹配 0 个
```

Discord 的真实结构是：
```
<div class="body_x">
  <div class="header_x">用户名 + 时间</div>   ← 和 messageContent 是兄弟
  <div class="messageContent_x">正文</div>
</div>
```

header 不是 messageContent 的后代。改用 `:has()` 从父级反查（Edge 157 / Chromium 157 支持）：
```js
'div:has(> [class*="messageContent_"]) > [class*="header_"]'
```

**坑 2：`isMetaLine` 判据过宽**

第一版写成「去掉日期时间后，剩下短名字且不含句末标点」。
结果 `Hahahaha the translation` 也满足（≤32 字符、没句号）→ **把普通聊天正文当元信息跳过了**。

修法：**必须先确认原文确实含日期/时间片段**，才可能是元信息行。

### 4.1.1 修复：真实 DOM 才暴露的两个问题

用户给出真实 Discord 的 DOM 后，发现两个我猜错的地方。

#### 坑 1：`data-list-id` 带了频道 ID 后缀

```html
<!-- 我以为的 -->
<div data-list-id="members">

<!-- 真实的 -->
<div role="list" aria-label="成员"
     data-list-id="members-128429929153464371">
                    ^^^^^^^ 带频道 ID！

<div role="listitem" data-list-item-id="members-128429929153464371__0">
```

精确匹配 `[data-list-id="members"]` → **匹配 0 个**，整个成员列表都没跳过。

修法：**前缀匹配**
```js
'[data-list-id^="members-"]',
'[data-list-item-id^="members-"]',
'aside[class*="membersWrap"]',
```

#### 坑 2：「服务器标签」被翻译成乱码

截图里出现「服务器标签: 高」「服务器标签: 星詠み」「服务器标签: VAL」。

原因：`shouldSkip` 只判**元素自己**是否命中选择器。
「服务器标签: HST」那个 div 自己没命中，但它**在成员项里面** → 漏了。

修法：新增 `ancestorSelectors` 字段，对成员列表用 `closest()` 上溯：

```js
ancestorSelectors: [
  '[data-list-id^="members-"]',
  'aside[class*="membersWrap"]',
],
```

**关键：这个能力只给明确标记的规则用** —— 不能无条件 closest，
早先的注释里写过：无条件上溯会把整棵消息树算成「在侧栏里」，导致整站不翻。

### 4.1.2 修复：**同一个站有多条规则时，只有第一条生效**（本次真凶）

用户贴出完整真实 DOM 后，我找到了真正的根因。

#### 根因

```js
function matchSiteRule() {
  for (var i = 0; i < SITE_RULES.length; i++) {
    if (SITE_RULES[i].host.test(host)) return SITE_RULES[i];   // ← 匹配第一个就 return
  }
}
```

Discord 有**两条**规则：

| # | 规则 | 内容 |
|---|---|---|
| ① | 导航壳 | 服务器图标栏 + 频道列表 |
| ② | 元信息 + 成员列表 | 用户名/时间 + 右侧成员列表 |

① 排在前面 → 先命中就 return → **② 永远不生效**。

所以前面几版我加的选择器、ancestorSelectors、文本启发式，**全是死代码**。

#### 修法：返回数组 + 聚合视图

```js
function matchSiteRules() {
  var hits = [];
  for (...) if (SITE_RULES[i].host.test(host)) hits.push(SITE_RULES[i]);
  return hits;
}

function siteSelectors() {
  // 把**所有**命中规则的 selectors / ancestorSelectors 合并成一个视图
  // 判定时「任意一条命中就算命中」
}
```

| 元素 | 选择器 | 之前 |
|---|---|---|
| 分组标题「Bot — 2」 | `h3[class*="membersGroup"]` | ❌ 没写 → 被翻 |

#### 4.1.2 附带修复：`properNounRows` 被转成了 boolean

重构 `siteSelectors()` 时，我把 `properNounRows` 聚合成了 boolean：

## 三十五、反向翻译：中文 → 外语（v4.2.0）

### 需求

> 像划词翻译一样，但反过来：用户在聊天框/输入框里打完中文，
> 左键划词选中，右键菜单里选「翻译为英、日、韩、葡等外国语言」。

### 与正向划词翻译的区别

| | 正向（dsh-selection） | 反向（dsh-reverse） |
|---|---|---|
| 方向 | 外 → 中 | 中 → 外 |
| 目标 | `cfg.targetLang`（固定） | 用户每次现选（10 种） |
| 位置 | 普通页面选区 | **输入框内** |
| 输出 | 只看气泡 | 看面板 + **可替换原文** |

### 10 种目标语言

英语 English · 日语 日本語 · 韩语 한국어 · 葡萄牙语 Português ·
法语 Français · 德语 Deutsch · 西班牙语 Español · 俄语 Русский ·
意大利语 Italiano · 繁體中文

### 提示词的关键约束

```js
'把下面的中文用' + L.native + '表达出来（' + L.zh + '）。',
'只输出' + L.native + '译文，不要输出中文原文，不要解释，不要加注音。',
'保留原文里的 {占位符}、@提及、URL、代码片段、表情符号不动。',
```

三个坑：

1. **必须写语言自称**（English / 日本語），不能只写中文名「英语」
   —— 实测只写后者，模型有时会把中文原样返回
2. **必须禁止注音**，否则日语会输出「日本語（にほんご）」这种
3. **必须声明保留占位符**，否则 `{path}`、`@张三` 会被翻掉

### 选区怎么拿（实测结论）

右键时浏览器**不会**清掉输入框里的选区：

```
textarea:
  mousedown  → start=0 end=34 selected="I want to translate this sentence "
  mouseup    → 同上
  contextmenu → 同上   ← 关键：没被清掉
```

但有个坑：**`document.activeElement` 有时会变成 body**，
所以 `grabReverseTarget()` 的判定顺序改成：

```
① 收集候选（焦点元素 + 选区祖先里可编辑的）
② 候选自身能给出选区文本 → 用它
③ 候选给不出，但 msg.text 非空 → 用 msg.text，
   再用 indexOf 在 value 里反查位置（保证替换仍可用）
```

### 替换原文：必须用 execCommand

```js
document.execCommand('insertText', false, newText);
```

为什么不能直接 `el.value = x`：React / Vue 受控组件监听**原生 input 事件**，
直接赋值不触发 onChange → 组件状态和 DOM 不一致，用户再输入一个字就整段回滚。

`execCommand('insertText')` 走浏览器原生编辑路径：触发 input 事件 + 自动进 Undo 栈。

兜底链：`execCommand` → `setRangeText` + 手动派发 input → 失败。

### 端到端实测

```
   input:          kind=input           text="这个功能我已"
   contenteditable: kind=contenteditable text="你好 @张三 ，"

③ 替换原文（三种都成功）

   input:    替换=true

```
